# Encrypted local storage design

Amid uses Foundation, CryptoKit AES-256-GCM and Security.framework only. This is original MIT code; no third-party storage engine or runtime service is required. Storage is opt-in. Before the explicit onboarding choice, the actor creates neither a Keychain item nor a store and keeps no raw history. Off keeps at most fifteen minutes in RAM; encrypted preferences remain available across launches. App-owned persistent raw process snapshots are never written.

## Format and key

The app-specific generic-password Keychain item uses service `com.madeordinary.amid.history`, account `encryption-key-v1`, and `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. It is 32 random bytes generated by CryptoKit. Loading requires an existing key and never creates a substitute for a missing key. The only Keychain operations target this exact app-owned service/account. Tests inject generated ephemeral keys and do not use real Keychain credentials.

Each file contains the four-byte marker `AMID` followed by the CryptoKit combined AES-GCM nonce/ciphertext/tag. The marker is authenticated as associated data. Nonces are freshly generated by CryptoKit. Codable JSON exists only in memory before encryption or after authenticated decryption. Preferences, aliases, exclusions, project boundaries, group IDs/names, alert details and minimal action IDs are encrypted. UserDefaults is not used by this subsystem. Numeric bucket timestamps/resolution in filenames do not identify an application/project.

The app-owned directory is mode 0700. Ciphertext staging files are created with O_EXCL/O_NOFOLLOW and mode 0600, fsynced, and atomically renamed. No plaintext journal, temporary file or database exists. Current directory/file symlinks and nonregular files fail closed. Other processes running as the user, compromised OS state, original files, exports, backups and crash dumps are outside the encryption/deletion guarantee.

## Transactions, versions and recovery

Version 3 uses immutable per-minute/per-hour encrypted bucket generations and an encrypted manifest. Each manifest lists the exact generation filenames it commits. New ciphertext generations are written first and their directory entries are synchronized. Atomic manifest replacement commits membership; its directory metadata is synchronized before any superseded/uncommitted buckets are deleted. A final directory synchronization follows garbage collection. Every failed synchronization stops the commit and reports store unavailable. Loading reads only authenticated manifest membership. An interrupted write cannot resurrect an excluded record by placing an orphan bucket in the directory. Garbage collection removes unlisted buckets after a successful authenticated commit. Immutable generations avoid exposing a newly rolled hour alongside its old constituent minutes after a crash.

Version 1/2 encrypted aggregate archives migrate in memory, enforce current retention, and commit version 3. New preference/load fields have backward decoding defaults. Unknown versions, missing committed generations, unavailable keys and authentication/decoding failures show store unavailable and preserve existing disk content. Ingestion does not silently replace a failed store. Unlocking and retrying load can recover a key-availability failure; explicit Clear History can recover an intentionally discarded corrupt store. No plaintext fallback exists.

## Aggregation and controls

Raw RAM samples are bounded to fifteen minutes and cleared on lock/quit by the app lifecycle. Persistent buckets contain application/project/system CPU and memory count/min/max/average; system buckets also contain load averages 1/5/15 minutes, swap and pressure states. RAM used by the system aggregate is active memory, distinct from per-process physical footprint/RSS. Cadences, partial measurements, observed duration and discontinuity duration are retained; per-metric coverage distinguishes missing CPU/memory from zero. A gap produces no synthetic zero samples. Repeated/out-of-order raw samples are ignored.

Minutes older than 24 hours roll into hours, merging weighted sums/counts and extrema rather than averaging averages. Retention (Off/24h/7d/30d) is enforced before the storage cap. The 250 MiB cap includes active ciphertext buckets and manifest. Whole oldest time buckets are evicted only after retention/rollups; `shortenedByCap` informs the user. Atomic replacement may briefly require room for the new ciphertext generation alongside the previous one. Settings too large to fit fail closed rather than silently truncating aliases.

Exclusions filter processes before app/project persistence and suppress identifying alert/action records. Adding an app exclusion conservatively purges existing derived project aggregates; changing project exclusions purges old app aggregates because historical partial app totals cannot safely subtract that project's contribution. Aliases affect display names independently from identity and use raw application IDs/project paths. Pause stops new persistent aggregates and alert/action recording. Lower retention immediately purges old history. Clear History deletes active generations, manifest, alert/action records and RAM caches, preserving encrypted preference/alias choices. It does not promise forensic SSD erasure.

The actor keeps a catalog of authenticated bucket generations and one mutable minute, with a per-minute index for incoming groups. Startup authenticates every committed bucket before exposing usable history. Maintenance reads affected buckets and writes replacement ciphertext one bucket at a time; it does not retain all archive rows or all encoded output at once. Only changed time buckets are encrypted at minute boundaries; unchanged historical hours are reused. Continued alert events save at most once per minute except new eligible events/recovery. Empty alert batches do not write.

Normal UI refresh reads metadata and requests the selected entity/range. At most two entity queries cache selected points by immutable generation; moving time bounds reuse unaffected buckets. Historical entities remain selectable after their processes exit. Query results are chronological and preserve missing values, gaps, metric methods and inclusive endpoints. The UI invalidates results before exclusion, Clear, lock, sleep, hide and quit transitions, then rejects stale replies. `state()` explicitly materializes the archive for diagnostics and tests; production UI and verification startup counts use metadata instead. Collector/storage work runs off the main actor.

Paging removes the ordinary version 3 full-archive working set. It does not guarantee a fixed total RSS: legacy inline archives still migrate through a complete authenticated decode, each individual encrypted bucket is materialized, inline events/actions and a high-churn entity directory can grow, and the live raw ring and GUI have their own cost. First-query latency and complete app memory/CPU require measurements; a disk cap is not a RAM bound.

## Alerts

The five published PRD thresholds are implemented with continuous observed windows. App CPU is time-weighted and includes raw/normalized average units. App memory growth requires at least 1 GiB and 25% over 30 minutes with a consistent supported method. Swap requires continuous warning/critical pressure plus 1 GiB growth in 15 minutes. Pressure triggers at 60 seconds and recovers after five normal minutes. Capacity requires five minutes below the user threshold and includes the OS definition. Other rules recover when their measured condition clears; missing values suspend evidence and reset qualification instead of claiming recovery. Actual rule/exclusion/threshold changes suspend observations without deleting old events. Identical alert settings leave continuous windows intact, so unrelated aliases/menu/login/notification preference saves cannot erase qualifying history. Category/entity notification cooldown is one hour; persisted last-notification time survives relaunch. Low-activity recovery requires a known thirty-minute weighted CPU average of at least 1% of one core; losing the two-hour qualification after missing data does not by itself recover an episode. Low observed CPU is in-app only: a recognized native development listener must be continuously observed for two hours and average below 1% of one core over its last thirty minutes. No client/traffic/safe-stop inference is made.

## Evidence and limitations

Focused tests cover Off/default privacy, encrypted aliases, permissions, wrong/unavailable keys, v1 migration, unknown-version preservation, gaps/spikes, exclusions, pause/clear, retention/forced cap, orphan-bucket recovery, symlinks, each alert trigger, missing data, recovery, method changes, cooldown/relaunch and a low-CPU listener. A synthetic 31-day hourly fixture forces a small cap. A separate 30-day fixture groups 1,000 synthetic processes into twenty apps, uses hourly older fixtures and minute fixtures for the newest 24 hours. This validates aggregation/storage behavior; it is not a thirty-day wall-clock run or a reference-M1 overhead result. Final observed test counts/timing are recorded by the integration owner. Real Keychain lock/reunlock, abrupt power loss, minimum-OS behavior, APFS disk-full recovery, real 30-minute observer budgets and two-week alert dogfooding still require their own observations.

Observed 2026-10-01 on arm64 macOS 27.0.1 using the installed Xcode toolchain: the focused full suite completed 17 tests with zero failures and one optional Keychain skip in 235.38 seconds. The 1,000-process synthetic soak passed in 232.94 seconds; the forced-cap soak passed in 2.36 seconds. After subsequent alert/UI API refinements, the seven alert tests plus orphan-generation regression passed again. The optional Keychain test initially returned `errSecParam` (-50) inside the execution sandbox. Running that exact isolated test with approved access outside the execution sandbox passed in 0.035 seconds: a fresh random `com.madeordinary.amid.history.test.<UUID>` namespace was confirmed absent, one 256-bit app-owned key was created and read, bytes matched, and that exact test-created item was deleted. Authentication interaction was disallowed; no existing credential was modified. This proves a normal host Keychain round trip, not lock/reunlock behavior.

Directory durability follow-up observed 2026-10-02: four focused tests passed with zero failures in 0.017 seconds. Injected interruption after durable generation creation preserves the previous manifest/generations; interruption after durable manifest commit but before garbage collection reloads the new committed membership and cannot resurrect excluded data. Existing orphan-generation and metric-rollup regressions also passed. These tests validate ordering and recoverability at injected commit boundaries; they do not claim actual abrupt-power-loss or storage-hardware cache guarantees.

Owned HFS+ exhaustion/recovery was observed in the [coverage follow-up](evidence/coverage-followup.md): real filler ENOSPC, generic fail-closed store/query errors, unchanged committed ciphertext and exact prior-record recovery. The fixed image was normally detached and removed. Store syscall errno, APFS and abrupt-power-loss behavior remain outside that result.
